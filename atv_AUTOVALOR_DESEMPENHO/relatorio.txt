RELATÓRIO - AUTOVALOR E AUTOVETOR (DESEMPENHO)
==============================================


1. O QUE FOI FEITO
------------------

Peguei o programa da atividade passada (método da potência com MPI) e medi
quanto tempo ele leva com:

    - diferentes tamanhos de matriz (n)
    - diferentes números de processos (comm_sz)
    - diferentes números de passos do método (steps)

Depois calculei o speedup e a eficiência de cada caso.

A matriz é a mesma da atividade passada: n x n, com 2 na diagonal e 1 no
resto. O maior autovalor dela é n + 1.


2. O QUE MUDOU NO CÓDIGO
------------------------

a) Número fixo de passos (steps)

Antes o programa parava quando o autovalor parava de mudar. Agora ele faz
sempre o mesmo número de passos (steps), que vem da linha de comando:

    ./autovalor_tempo n steps

Assim dá pra comparar o tempo de forma justa.

b) Tempo medido só na região de interesse

A região de interesse é o laço do método da potência (multiplicar, calcular
o autovalor, normalizar e juntar o x). Ficaram de fora do tempo a criação da
matriz e o MPI_Scatter.

    MPI_Barrier(MPI_COMM_WORLD);       -> espera todo mundo chegar
    double t0 = MPI_Wtime();           -> marca o começo

    ... laço do método da potência ...

    double t1 = MPI_Wtime();           -> marca o fim
    MPI_Reduce(&tempo_local, &tempo, 1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);

O MPI_Barrier faz todos os processos começarem a contar juntos. No final,
o MPI_Reduce com MPI_MAX pega o tempo do processo mais lento, porque o
programa só termina quando o último processo termina.


3. SPEEDUP E EFICIÊNCIA
-----------------------

Speedup: quantas vezes ficou mais rápido em relação a 1 processo.

    speedup = tempo com 1 processo / tempo com p processos

Eficiência: o quanto cada processo foi bem aproveitado (1 = 100%).

    eficiência = speedup / p

Exemplo: se com 1 processo leva 8 s e com 4 processos leva 2,5 s:

    speedup    = 8 / 2,5 = 3,2   (ficou 3,2 vezes mais rápido)
    eficiência = 3,2 / 4 = 0,8   (80% de aproveitamento)

O ideal seria speedup = p e eficiência = 1, mas isso quase nunca acontece,
porque os processos perdem tempo se comunicando.


4. O CÓDIGO (autovalor_tempo.c)
-------------------------------

#include <stdio.h>
#include <stdlib.h>
#include <math.h>
#include <mpi.h>

int main(int argc, char* argv[]){
    int comm_sz;
    int my_rank;

    int n = 1024;
    int steps = 100;
    if(argc > 1) n = atoi(argv[1]);
    if(argc > 2) steps = atoi(argv[2]);

    MPI_Init(&argc, &argv);
    MPI_Comm_size(MPI_COMM_WORLD, &comm_sz);
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);

    if(n % comm_sz != 0){
        if(my_rank == 0) printf("Erro: n = %d precisa ser multiplo de p = %d\n", n, comm_sz);
        MPI_Finalize();
        return 1;
    }

    int linhas = n / comm_sz;

    double *A = NULL;
    if(my_rank == 0){
        A = malloc((long)n * n * sizeof(double));
        for(int i=0; i<n; i++){
            for(int j=0; j<n; j++){
                if(i == j) A[(long)i*n + j] = 2.0;
                else A[(long)i*n + j] = 1.0;
            }
        }
    }

    double *A_local = malloc((long)linhas * n * sizeof(double));
    MPI_Scatter(A, linhas * n, MPI_DOUBLE, A_local, linhas * n, MPI_DOUBLE, 0, MPI_COMM_WORLD);

    if(my_rank == 0){
        free(A);
        A = NULL;
    }

    double *x = malloc(n * sizeof(double));
    double *y_local = malloc(linhas * sizeof(double));
    double *x_local = malloc(linhas * sizeof(double));

    double norma = 0.0;
    for(int i=0; i<n; i++){
        x[i] = i + 1;
        norma += x[i] * x[i];
    }
    norma = sqrt(norma);
    for(int i=0; i<n; i++){
        x[i] = x[i] / norma;
    }

    int inicio = my_rank * linhas;
    double lambda = 0.0;

    MPI_Barrier(MPI_COMM_WORLD);
    double t0 = MPI_Wtime();

    for(int k=0; k<steps; k++){
        for(int i=0; i<linhas; i++){
            double soma = 0.0;
            for(int j=0; j<n; j++){
                soma += A_local[(long)i*n + j] * x[j];
            }
            y_local[i] = soma;
        }

        double xAx_local = 0.0;
        for(int i=0; i<linhas; i++){
            xAx_local += x[inicio + i] * y_local[i];
        }
        double xAx;
        MPI_Allreduce(&xAx_local, &xAx, 1, MPI_DOUBLE, MPI_SUM, MPI_COMM_WORLD);

        double xx = 0.0;
        for(int i=0; i<n; i++){
            xx += x[i] * x[i];
        }

        lambda = xAx / xx;

        double norma_local = 0.0;
        for(int i=0; i<linhas; i++){
            norma_local += y_local[i] * y_local[i];
        }
        MPI_Allreduce(&norma_local, &norma, 1, MPI_DOUBLE, MPI_SUM, MPI_COMM_WORLD);
        norma = sqrt(norma);

        for(int i=0; i<linhas; i++){
            x_local[i] = y_local[i] / norma;
        }
        MPI_Allgather(x_local, linhas, MPI_DOUBLE, x, linhas, MPI_DOUBLE, MPI_COMM_WORLD);
    }

    double t1 = MPI_Wtime();
    double tempo_local = t1 - t0;
    double tempo;
    MPI_Reduce(&tempo_local, &tempo, 1, MPI_DOUBLE, MPI_MAX, 0, MPI_COMM_WORLD);

    if(my_rank == 0){
        printf("%d,%d,%d,%.6f,%.6f\n", n, comm_sz, steps, tempo, lambda);
    }

    free(A_local);
    free(x);
    free(y_local);
    free(x_local);
    MPI_Finalize();
    return 0;
}


5. COMO FOI MEDIDO
------------------

Rodei no supercomputador NPAD (UFRN), na partição amd-512.

Valores testados:

    n (tamanho da matriz): 2048, 4096, 8192 e 16384
    steps (passos):        10, 50 e 100
    comm_sz (processos):   1, 2, 4, 8, 16, 32 e 64

Todos os n são múltiplos de 64, então são múltiplos de todos os comm_sz
testados (cada processo recebe o mesmo número de linhas).

Nós e processos por nó:

    comm_sz de 1 até 32 -> 1 nó
    comm_sz = 64        -> 2 nós com 32 processos em cada

Antes de começar, o script roda o programa uma vez sem guardar o resultado,
só pra "aquecer".

Script usado (job_desempenho.sh):

#!/bin/bash
#SBATCH --job-name=autovalor_tempo
#SBATCH --output=resultados.csv
#SBATCH --error=erros.txt
#SBATCH --partition=amd-512
#SBATCH --nodes=2
#SBATCH --ntasks-per-node=32
#SBATCH --time=0-1:00

echo "$SLURM_JOB_NODELIST" > nos_alocados.txt

mpirun -np 1 ./autovalor_tempo 512 10 > /dev/null

echo "n,p,steps,tempo,autovalor"

for n in 2048 4096 8192 16384
do
    for steps in 10 50 100
    do
        for p in 1 2 4 8 16 32 64
        do
            mpirun -np $p ./autovalor_tempo $n $steps
        done
    done
done

As tabelas e os gráficos foram feitos pelo script graficos.py, que lê o
arquivo resultados.csv.

8. CONCLUSÃO
------------

- O autovalor calculado foi n + 1 em todos os casos (2049, 4097, ...), que é
  o valor certo. Mudar o número de processos não muda a resposta.

- Até 32 processos (tudo no mesmo nó), o speedup ficou perto do ideal. Com
  n = 2048 e steps = 100, por exemplo:

      p = 2  -> speedup 2,0  (eficiência 1,00)
      p = 8  -> speedup 7,6  (eficiência 0,95)
      p = 32 -> speedup 27,2 (eficiência 0,85)

  A eficiência vai caindo aos poucos, porque cada processo faz menos conta,
  mas a comunicação (MPI_Allreduce e MPI_Allgather) continua acontecendo em
  todo passo.

- Com 64 processos o programa passa a usar 2 nós, e a comunicação entre nós
  diferentes é bem mais lenta que dentro do mesmo nó. Aí a eficiência cai
  bastante. Com n = 2048 e steps = 100, o speedup foi 29,9 (eficiência 0,47),
  quase igual ao de 32 processos.

- O número de steps fez diferença justamente com 64 processos. Com n = 2048:

      steps = 10  -> speedup 4,1  (64 processos foi MAIS LENTO que 32)
      steps = 50  -> speedup 22,0
      steps = 100 -> speedup 29,9

  A primeira comunicação entre os 2 nós tem um custo fixo (preparar a
  conexão). Com poucos steps, esse custo pesa muito no tempo total. Com mais
  steps, ele se dilui. Até 32 processos (1 nó só), os steps quase não mudam
  o speedup.

- Quanto maior a matriz (n), melhor o aproveitamento com 64 processos,
  porque cada processo tem mais conta pra fazer e a comunicação pesa menos.
  Com steps = 10, por exemplo, n = 2048 deu speedup 4,1 e n = 4096 deu 35,3.

- Durante a execução, o MPI avisou que não conseguiu usar a placa de rede
  rápida (InfiniBand) dos nós e usou outra forma de comunicação. Isso não
  muda os resultados das contas, mas deixa a comunicação entre os 2 nós mais
  lenta, o que ajuda a explicar a queda de eficiência com 64 processos.
